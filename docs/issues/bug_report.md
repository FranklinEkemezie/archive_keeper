# Bug Report - Archive Keeper

This document details bugs, unimplemented features, and badly implemented features as compared against SPECS.md.
Generated by analysis of codebase (src/main.rs), tests (tests/cli.rs), and specification.


## EXECUTIVE SUMMARY

All 5 CLI integration tests pass. However, the implementation has several issues when compared against SPECS.md including:
- Critical logic bugs in ID/document slot management
- Missing/incorrect validation behavior
- UX and spec compliance issues
- Design issues that could cause problems even with current tests


## 1. DOCUMENT ID MANAGEMENT (CRITICAL BUGS)

### BUG-001: ID generation is broken - uses separate counters incorrectly
**Location:** `app_data_generate_document_id()` and `app_data_insert_document()` - lines ~485-510 in main.rs
**Severity:** High (Core functionality)
**Spec reference:** "Each registered document must receive a unique identification number that the application assigns automatically." (Sec 2)

**How it works now:**
- `AppData = (last_document_id, next_available_document_id, document_repository)`
- `app_data_generate_document_id()` does: `app_data.0 += 1; app_data.0` (increments last_saved_document_id and returns it)
- `app_data_insert_document()` calls `app_data_get_next_available_document_id()` which does `app_data.1 += 1; app_data.1` (increments next_available_id) and then uses it as array index `app_data.2[next_id] = document`

So for first registration:
- `app_data_generate_document_id()` returns 1 (last_document_id becomes 1), ID returned is 1
- `app_data_insert_document()` gets next_id = (next_available_id becomes 1) and stores at index 1
- But repository is indexed by slot number; the "ID" given to user is 1

Also look at initial state:
```rust
let last_document_id: DocumentId = INITIAL_DOCUMENT_ID; // 0
let next_available_id: DocumentId = INITIAL_DOCUMENT_ID; // 0
```
And INITIAL_DOCUMENTS all have placeholder=true, IDs 0-9.

But this means the array slot used is `next_available_id` after incrementing - so first insert goes to slot index 1, second goes to slot 2 etc. That means slot 0 (ID 0 in initial data) is never used? Also the ID value is independent from slot index - they happen to be same in current flow by coincidence of increments. This is confusing/badly implemented.

**Issue 1:** The counters are incremented separately and don't maintain consistency. The logic is error-prone.
**Issue 2:** The comment says "Handle borrowing, deletion and when document repository is full" - but with fixed array of 10 and this scheme, after inserting 10 docs, next_id becomes 10 and we do `app_data.2[next_id]` which is an index out of bounds panic! (array is 0..9). The tests only insert up to 2 docs, so they pass.

**Reproduction:**
1. Register 10 documents - after 10th registration, app will try to write to index 10 of a 10-element array (indices 0-9) causing panic.
2. This is a correctness issue per "max capacity" not specified but implementation is fixed size.


### BUG-002: Document is inserted at wrong index
**Location:** app_data_insert_document() (line ~504-510)
```rust
let next_id = app_data_get_next_available_document_id(app_data) as usize;
app_data.2[next_id] = document;
```
next_available_id starts at 0, increments to become 1, so stores in index 1. The placeholder at index 0 remains placeholder forever. The "last_document_id" (app_data.0) is what determines the returned ID. These are coupled in a weird way.

Also the first registered document gets ID = last_document_id becomes 1, stored at index 1. Second: ID becomes 2, stored at index 2. So documents never occupy index 0 in normal flow? Index 0 stays as initial placeholder with ID 0. That’s odd but not directly breaking current behavior.

But this is badly implemented design - confusing naming and structure. Also means we waste index 0.

**Impact:** Works for current tests but is fragile and incorrect for general case.


### BUG-003: No bounds check when repository is full
**Spec:** No explicit max stated except implied by practical use. But implementation has MAX_NUM_OF_DOCUMENT=10 with fixed array. When full, we should handle gracefully per "Input and Error Handling" - reject operation without crashing.
**Current:** Will panic with index out of bounds (attempting to access index 10+ on [Document; 10])

**Reproduction idea:** Register 10 documents successfully, try to register 11th - panic due to array indexing.


## 2. DOCUMENT CREATION & VALIDATION

### BUG-004: Validation occurs after generating ID - ID is wasted if validation fails
**Location:** main_menu_register_document() (line ~343-396)
**Flow:**
1. Prompt for title, author, category, year
2. Generate ID via app_data_generate_document_id() (increments counter) - line ~379
3. Create document via document_create() - may panic if validation fails (empty strings, invalid category/year) - lines ~637-662
4. Insert document - line ~389-396

But document_create() panics on invalid input (title empty, author empty, invalid category, invalid year). Also in the menu flow, they already validate year themselves (lines ~357-372), but they don’t validate title/author emptiness before generating ID. So if user enters empty title after UI prompts, document_create() panics.

Also spec says: "The application must not allow a document to be registered if any required information is missing or invalid. ... Where an operation fails, the application should preserve the existing archive data." (Sec 2, Sec 8). Panicking on invalid input violates "handle invalid input gracefully and explain what went wrong in ordinary language" and "should handle unexpected input without panicking under normal usage".

**Reproduction:**
- Try to register with empty title - app will panic with "title cannot be empty" (from document_create at line ~645-648). This is bad UX and violates spec.


### BUG-005: Year validation - correct logic but message format is fine; but what about non-numeric input?
**Location:** main_menu_register_document() lines ~357-372
```rust
let input = ui_prompt_user_uint("Year") as DateYear;
if ! (input >= MIN_VALID_DOCUMENT_YEAR && input <= CURRENT_YEAR) {
    ui_print_error_msg(&std::format!("Year must be between {MIN_VALID_DOCUMENT_YEAR} and {CURRENT_YEAR}"));
    continue;
}
```
ui_prompt_user_uint reads via ui_prompt_user_int then checks if negative - returns u32. So entering non-numeric gives "Invalid input. Please enter a number" (from ui_prompt_user_int at line ~302-317). That’s graceful.

Also spec states year must be 1900..current year (2026). CURRENT_YEAR is hardcoded to 2026. This is fine as long as app is built now.


### BUG-006: document_create panics on invalid input instead of returning Result
**Location:** document_create() lines ~637-662
Panics on: empty title, empty author, invalid category, invalid year. But category comes from document_category_prompt_category() which only returns valid values or panics itself (line ~705-733) - so category is safe if prompt works. Year is validated before calling. But title/author are trimmed - if user enters only spaces, trim gives empty string → panic.

**Spec violation:** "handle invalid input gracefully and explain what went wrong in ordinary language" (Sec 8). "should handle unexpected input without panicking under normal usage" (Sec 8).


### BUG-007: Inconsistent validation for title/author
**Location:** ui_prompt_user() just reads line and trims (line ~276-300). Empty string after trim is possible. But spec says "The application must not allow a document to be registered if any required information is missing or invalid." So empty title/author are missing/invalid - must be rejected with clear message, not crash.

**Current behavior:** crash via panic in document_create().

### BUG-013: Input type - ID entered as int
Line ~516 does `ui_prompt_user_int("Enter document ID") as DocumentId`. If user enters negative, ui_prompt_user_int returns negative i32 (line ~302-317: it parses as i32, doesn't check negative). Then cast to DocumentId (u32) - negative becomes large positive u32 in Rust cast? Let us check.

So entering "-1" would become a huge u32, likely not matching any doc - so it would fail to find and say "No document with ID..." which is a graceful handling in effect. But it's not the most user-friendly message. Spec says "entering letters where a number is expected" is example of invalid input - negative numbers aren't explicitly mentioned. But behavior is safe.

Also if user enters non-numeric, ui_prompt_user_int gives "Invalid input. Please enter a number" and loops - good.

## 8. MENU & UX

### OBS-006: Main menu loop
Loop continues until option 0 returns false from handler - main_menu_exit_app() returns false, so loop breaks. Correct per "application should remain usable until employee chooses to exit" and "can perform multiple operations during one execution and exit deliberately".

### OBS-007: Invalid menu selection
main_menu_handle_option panics on unknown option (_ => panic!("Unknown option: {option}")). But wait - look up how it's called.

In main: `let option = main_menu_prompt(); if ! main_menu_handle_option(option, &mut app_data) { return; }`
main_menu_prompt calls ui_prompt_user_menu_option with max_option 6. ui_prompt_user_menu_option loops while option > max_option (line ~330-346). So option is always 0..=6 when returned from prompt. ## 9. CRITICAL STRUCTURAL ISSUES

### BUG-015: app_data_get_next_available_document_id() is wrong and misleading
**Location:** ~492-498
```rust
fn app_data_get_next_available_document_id(app_data: &mut AppData) -> DocumentId {
    // TODO: Handle borrowing, deletion and when document repository is full.
    app_data.1 += 1;
    app_data.1
}
```
- It increments and returns the incremented value. But it's used as an ARRAY INDEX (line ~507). So the return type DocumentId (u32) is semantically wrong for indexing - should be usize. Also naming is confusing - "next available document ID" suggests returning an ID value, but we use it as slot index.
- Also the logic is completely broken for any realistic case - it just takes next_index++ sequentially, never reuses freed slots (placeholders). But deletion is not mentioned in spec; borrowing doesn't free slots. So maybe not an issue for this spec.
- But the comment indicates known issue.


### BUG-016: Using fixed array [Document; 10] limits to 10 documents total
**Location:** types - MAX_NUM_OF_DOCUMENT = 10, DocumentRepository is fixed array
**Spec:** No explicit limit stated. But with in-memory only and small scale, maybe acceptable. However, the implementation will panic when trying to insert beyond 10 (index out of bounds as noted in BUG-003). Also no graceful error message.

This is a correctness/robustness issue per "handle invalid operations gracefully" - registering when full is an operation that cannot be completed successfully; should give clear message, not crash.


### BUG-017: ID generation could theoretically collide in confusing ways
With separate counters (last_document_id vs next_available_id), the code is hard to reason about. Also if we had reuse logic, it would be messy. Current approach "works" for sequential inserts as long as array has space.


### BUG-018: Searching by category matches the display label (case-insensitive, partial)
Yes - correct. For example "research" matches "Research Paper". Good.

## 12. SUMMARY OF KEY ISSUES

### High Severity
1. **BUG-001/002/015:** ID generation/indexing logic is confusing and fragile; using separate counters is bad design
2. **BUG-003:** No bounds checking - will panic if archive fills to capacity
3. **BUG-004/006/007:** Panics on invalid input (empty strings) instead of graceful error handling with messages - violates "handle invalid input gracefully and explain what went wrong in ordinary language" and "should handle unexpected input without panicking under normal usage"

### Medium Severity
1. **BUG-013:** Negative IDs cast to large u32 - odd behavior (but harmless)
2. **OBS-003:** Long titles/authors truncated in table display (UX issue)

### Low/Design Issues
1. Fixed array of 10 is very restrictive; Vec<Document> would be better design
2. Many panics in internal functions for "shouldn't happen" cases - not ideal for robustness
3. Type aliases like `type Option = u8;` shadowing std::Option conceptually in naming (confusing in codebase)


## 13. RECOMMENDATIONS FOR FIXING (FOR REFERENCE ONLY - NOT IMPLEMENTED)

- Replace fixed array with Vec<Document> to avoid capacity issues
- Use a single source of truth for IDs; track next ID and occupied slots properly
- Return Result<T,E> from validation functions instead of panicking
- Validate empty/whitespace strings in UI layer with clear error messages and retry loop
- Add bounds check before inserting; show user-friendly error if archive is full
- Consider that negative numbers from int input should be rejected explicitly with message

Note: Per user instruction, NOTHING has been fixed or edited. This report is purely observational.
